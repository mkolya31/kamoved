# 02. Статус требований проекта «Камовед»

**Дата среза:** 13 августа 2026 года  
**Назначение:** сопоставить актуальные бизнес- и технические требования с фактическим состоянием приложения.

## Обозначения

| Статус | Значение |
|---|---|
| ✅ Реализовано | Требование доступно пользователю или полностью обеспечено технически |
| 🟡 Частично | Реализована только часть сценария либо подготовлен технический каркас без законченного пользовательского процесса |
| 🔵 В работе | Изменения присутствуют локально, но ещё не зафиксированы в основной ветке |
| ❌ Не реализовано | Пользовательский сценарий и необходимая серверная логика отсутствуют |

## Бизнес-требования

| Требование | Статус | Что уже работает / чего не хватает |
|---|---|---|
| Авторизация продавца | ✅ Реализовано | Работают вход по логину и паролю, серверная сессия, выход и защита API от неавторизованных запросов |
| Продажа из наличия | ✅ Реализовано | Продавец может создать продажу с одной или несколькими позициями; система автоматически устанавливает статусы «Оплачено» и «Завершён» |
| Комментарий к продаже из наличия | ❌ Не реализовано | Нужно необязательное поле для служебных пометок продавца, например о выдаче сдачи из собственных денег. Поле не должно замедлять основной сценарий создания продажи |
| Позиции продажи | ✅ Реализовано | Поддерживаются название, количество, единица измерения, цена за единицу и рассчитанная сумма позиции |
| Единицы измерения | ✅ Реализовано | Поддерживаются штуки, квадратные метры, погонные метры и упаковки; при отсутствии единицы backend использует штуки |
| Расчёт суммы | ✅ Реализовано | Backend самостоятельно рассчитывает суммы позиций и общий итог; копейки отбрасываются в пользу клиента |
| Просмотр последних записей | ✅ Реализовано | Записи выводятся от новых к старым и визуально группируются по датам |
| Просмотр состава записи | ✅ Реализовано для продаж | Строку продажи можно раскрыть и увидеть все позиции, количество, цену и сумму |
| Информационное поле «Выручка сегодня» | ✅ Реализовано | Показывает сумму оплаченных и завершённых продаж текущего продавца за календарный день по московскому времени |
| Laptop-first интерфейс | ✅ Реализовано базово | Основной экран ориентирован на ноутбук; предусмотрены адаптивные стили для узких экранов |
| Режим «Все записи» | ✅ Реализовано | Открывается по умолчанию и показывает хронологическую ленту журнала |
| Режим «Активные заказы» | 🟡 Частично | Переключатель и серверная фильтрация по активным статусам готовы, но создавать сопровождаемые заказы пока нельзя |
| Пагинация журнала | 🟡 Частично | Backend поддерживает параметры `page` и `size`, но интерфейс загружает только первые 30 записей и не позволяет запросить следующие |
| Создание нового заказа | ❌ Не реализовано | Кнопка присутствует, но заблокирована; нет формы и API создания заказа |
| Клиент и дополнительные контакты | ❌ Не реализовано | Нет модели контактов, хранения нормализованных телефонов, API и формы ввода |
| Статусы оплаты заказа | 🟡 Частично | Значения `UNPAID`, `PREPAID` и `PAID` предусмотрены в модели, но пользователь не может назначать или изменять их у заказа |
| Предоплата и остаток к оплате | 🟡 Частично | Поле предоплаты существует в таблице журнала, но отсутствуют API, бизнес-валидация, расчёт остатка и интерфейс |
| Статусы исполнения заказа | 🟡 Частично | Все требуемые статусы описаны в модели и имеют русские подписи, но создавать заказ и менять его статус нельзя |
| Способ получения и адрес доставки | 🟡 Частично | Поля и допустимые значения существуют в модели БД, но отсутствуют в API и пользовательском интерфейсе |
| Комментарий к заказу | 🟡 Частично | Поле предусмотрено в БД, но его нельзя заполнить или увидеть в приложении |
| Просмотр полной карточки заказа | ❌ Не реализовано | Получение записи работает только для данных, которые есть у продажи; контакты, предоплата, получение, адрес и комментарий в DTO не входят |
| Редактирование заказа | ❌ Не реализовано | Нет `PATCH /api/orders/{id}` и формы редактирования |
| Быстрая смена статуса | ❌ Не реализовано | Статус заказа нельзя изменить ни в карточке, ни непосредственно из журнала |
| Поиск старых записей | ❌ Не реализовано | Нет поискового API и интерфейса поиска по телефону, имени, адресу и товару |
| Каталог и автоподстановка товара | ❌ Не реализовано | Позицию можно ввести вручную, но каталога, подсказок, автоматической единицы измерения и рекомендуемой цены нет |

## Технические требования

| Требование | Статус | Что уже работает / чего не хватает |
|---|---|---|
| Архитектура React → Spring Boot → PostgreSQL | ✅ Реализовано | Frontend, backend и база данных работают как единое веб-приложение |
| Модульный монолит backend | ✅ Реализовано | Код разделён как минимум на модули `auth`, `journal` и `common`; отдельные микросервисы не используются |
| React + TypeScript frontend | ✅ Реализовано | Интерфейс создан на React, TypeScript и Vite |
| Java 21 + Spring Boot backend | ✅ Реализовано | REST API, бизнес-логика, валидация и доступ к данным реализованы на Spring Boot |
| PostgreSQL | ✅ Реализовано | Основные данные хранятся в PostgreSQL; база не публикуется наружу в production Compose |
| Миграции Flyway | ✅ Реализовано | Созданы версионированные миграции пользователей, записей журнала и позиций |
| Модель пользователя | ✅ Реализовано | Хранятся логин, BCrypt-хеш пароля, отображаемое имя, признак активности и дата создания |
| Session-based authentication | ✅ Реализовано | Используется серверная HTTP-сессия Spring Security без собственной JWT-инфраструктуры |
| CSRF-защита | ✅ Реализовано | Изменяющие запросы выполняются с CSRF-токеном |
| Модель `JournalEntry` | 🟡 Частично | Основные поля, типы, статусы, суммы, автор, даты и версия существуют; контакты пока отсутствуют |
| Модель `JournalEntryItem` | ✅ Реализовано | Хранятся snapshot-название, количество, единица, цена и рассчитанная сумма; ссылка на будущий каталог необязательна |
| Серверный расчёт денег | ✅ Реализовано | Клиент не передаёт итоговые суммы; backend рассчитывает их через `MoneyCalculator` с `RoundingMode.FLOOR` |
| Транзакционное создание продажи | ✅ Реализовано | Запись и все позиции сохраняются в одной транзакции |
| `POST /api/sales` | ✅ Реализовано | Создаёт завершённую и оплаченную продажу текущего пользователя |
| `GET /api/journal` | ✅ Реализовано | Поддерживает режимы `all` и `active`, номер страницы и размер страницы |
| `GET /api/journal/{id}` | 🟡 Частично | Возвращает полные позиции и статусы продажи, но DTO ещё не содержит всех данных будущего заказа |
| Backend-фильтрация активных заказов | ✅ Реализовано | Активность вычисляется по типу `ORDER` и набору незавершённых статусов; отдельной таблицы активных заказов нет |
| Расчёт дневной выручки | ✅ Реализовано | Агрегация выполняется в БД отдельно от пагинации, по текущему продавцу и границам московского дня |
| `POST /api/orders` | ❌ Не реализовано | Нет создания заказа, контактов и связанной бизнес-валидации |
| `PATCH /api/orders/{id}` | ❌ Не реализовано | Нет изменения позиций, контактов, оплаты, исполнения, получения, адреса и комментария |
| Контакты `entry_contact` | ❌ Не реализовано | Нет таблицы, сущности, типов `CLIENT/ADDITIONAL` и ограничения одного основного клиента |
| Нормализация телефона | ❌ Не реализовано | Исходный и нормализованный телефоны не хранятся, поиск по цифрам отсутствует |
| Валидация позиции | ✅ Реализовано | Проверяются непустое название, положительное количество, неотрицательная цена и допустимая точность чисел |
| Валидация заказа | ❌ Не реализовано | Нет правил для предоплаты, адреса доставки и допустимых сочетаний статусов оплаты |
| Optimistic locking | 🟡 Частично | Поле `version` и аннотация `@Version` есть, но сценарий изменения заказа и обработка конфликта в UI отсутствуют |
| Поисковый API | ❌ Не реализовано | Нет `GET /api/journal/search`, SQL/JPQL-поиска и требуемых поисковых индексов контактов |
| Каталог товаров | ❌ Не реализовано | Нет таблицы `catalog_product`, API подсказок и autocomplete; в позиции подготовлено необязательное поле `catalogProductId` |
| Удаление записей | ✅ Соответствует требованию | API удаления сознательно отсутствует, чтобы сохранять устойчивую историю журнала |
| Отображение ошибок API | ✅ Реализовано базово | Backend возвращает структурированные ошибки, frontend показывает сообщения и предлагает повторить загрузку журнала |
| Локальный Docker Compose | ✅ Реализовано | PostgreSQL, backend и frontend запускаются одной Compose-конфигурацией |
| Production Docker Compose | ✅ Реализовано | Сервисы разделены внутренними сетями, frontend подключён к общей сети reverse proxy, для JVM задан лимит памяти |
| Nginx и HTTPS | ✅ Реализовано | Приложение подключено к общему Nginx; сертификаты выпускаются и обновляются через Certbot |
| Production-деплой | ✅ Реализовано | Подготовлены Compose-конфигурация, серверный deploy-скрипт и документация запуска |
| Автоматический деплой | ✅ Реализовано | Push в ветку `production` запускает GitHub Actions и ограниченный SSH-деплой на VPS |
| Секреты production | ✅ Реализовано | Секреты передаются через исключённый из Git файл `.env.production` и GitHub Actions secret |
| Резервное копирование PostgreSQL | ✅ Реализовано | Каждый час создаётся зашифрованный бэкап в приватном Timeweb S3; настроена ротация, ежемесячное тестовое восстановление и аварийная инструкция. Первый снимок успешно восстановлен вручную; внешний автоматический алертинг пока отсутствует |
| Ротация Docker-логов | ❌ Не реализовано | В Compose не заданы ограничения `max-size`/`max-file`, отдельная политика ротации не описана |
| Unit-тест расчёта денег | ✅ Реализовано | Проверены отбрасывание копеек и суммирование округлённых позиций |
| Интеграционный тест авторизации | ✅ Реализовано | Проверены успешный вход, создание сессии и отклонение неверного пароля |
| Интеграционный тест продажи | ✅ Реализовано | Проверены создание продажи, автоматические статусы и появление первой в журнале |
| Интеграционный тест дневной выручки | ✅ Реализовано | Проверены продавец, статусы, тип записи, московские границы дня и независимость от пагинации |
| Тесты активных статусов | 🟡 Частично | Интеграционный тест подтверждает отсутствие завершённой продажи в активных, но все статусы заказов отдельно не проверены |
| Тесты заказа, предоплаты и доставки | ❌ Не реализовано | Соответствующие пользовательские сценарии и серверная логика ещё отсутствуют |
| Тест поиска | ❌ Не реализовано | Поиск ещё не реализован |

## Общая готовность MVP

Из пяти ключевых пользовательских сценариев полностью готовы два:

1. Создать продажу из наличия.
2. Посмотреть последние записи журнала.

Режим активных заказов имеет техническую основу, но станет полезен только после появления сопровождаемых заказов. Создание заказа и поиск старых записей пока отсутствуют.

## Продуктовый бэклог

| Доработка | Статус | Предлагаемые границы |
|---|---|---|
| Комментарий к продаже из наличия | Запланировано | Добавить необязательное многострочное поле в форму прямой продажи, сохранять текст в существующем поле `journal_entry.comment` и показывать его при раскрытии записи. Пустой комментарий не хранить и не отображать |

## Рекомендуемая последовательность следующих доработок

1. **Создание нового заказа** — позиции, клиент и дополнительные контакты, оплата и предоплата, исполнение, способ получения, адрес и комментарий.
2. **Просмотр и изменение заказа** — прежде всего изменение статуса исполнения и защита от одновременного редактирования.
3. **Поиск** — по имени, телефону, адресу и товару.
4. **Каталог товаров** — autocomplete, предлагаемая единица измерения и цена с возможностью ручного изменения.
5. **Пользовательская пагинация** — загрузка записей старше первых 30.

Следующим вертикальным срезом рекомендуется создание нового заказа: он раскрывает ценность уже подготовленного режима «Активные заказы» и создаёт данные, по которым впоследствии должен работать поиск.
