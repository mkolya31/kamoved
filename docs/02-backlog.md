# 02. Бэклог и статус требований проекта «Камовед»

**Дата среза:** 14 августа 2026 года

**Назначение:** сопоставлять актуальные бизнес- и технические требования с фактическим состоянием приложения и поддерживать актуальный бэклог.

## Обозначения

| Статус | Значение |
|---|---|
| ✅ Реализовано | Требование доступно пользователю или полностью обеспечено технически |
| 🟡 Частично | Реализована только часть сценария либо подготовлен технический каркас без законченного пользовательского процесса |
| 🔵 В работе | Изменения присутствуют локально, но ещё не зафиксированы в основной ветке |
| ❌ Не реализовано | Пользовательский сценарий и необходимая серверная логика отсутствуют |

## Бизнес-требования

| Требование | Статус | Что уже работает / чего не хватает |
|---|---|---|
| Авторизация продавца | ✅ Реализовано | Работают вход по логину и паролю, сохранение входа после перезапуска браузера на срок не более 7 суток, немедленный выход и защита API; несколько пользователей настраиваются через `.env.production` без ролевой модели |
| Продажа из наличия | ✅ Реализовано | Продавец может создать продажу с одной или несколькими позициями; система автоматически устанавливает статусы «Оплачено» и «Завершён» |
| Комментарий к продаже из наличия | ❌ Не реализовано | Нужно необязательное поле для служебных пометок продавца, например о выдаче сдачи из собственных денег. Поле не должно замедлять основной сценарий создания продажи |
| Позиции продажи | ✅ Реализовано | Поддерживаются название, количество, единица измерения, цена за единицу и рассчитанная сумма позиции |
| Единицы измерения | ✅ Реализовано | Поддерживаются штуки, квадратные метры, погонные метры и упаковки; при отсутствии единицы backend использует штуки |
| Расчёт суммы | ✅ Реализовано | Backend самостоятельно рассчитывает суммы позиций и общий итог; копейки отбрасываются в пользу клиента |
| Просмотр последних записей | ✅ Реализовано | Записи выводятся от новых к старым и визуально группируются по датам |
| Просмотр состава записи | ✅ Реализовано | Строку продажи или заказа можно раскрыть и увидеть все позиции, количество, цену и сумму |
| Информационное поле «Выручка сегодня» | ✅ Реализовано | Показывает сумму оплаченных и завершённых продаж текущего продавца за календарный день по московскому времени |
| Laptop-first интерфейс | ✅ Реализовано базово | Основной экран ориентирован на ноутбук; предусмотрены адаптивные стили для узких экранов |
| Режим «Все записи» | ✅ Реализовано | Открывается по умолчанию и показывает хронологическую ленту журнала |
| Режим «Активные заказы» | ✅ Реализовано | Переключатель показывает созданные заказы с незавершёнными статусами исполнения; завершённые и отменённые записи исключаются сервером |
| Пагинация журнала | 🟡 Частично | Backend поддерживает параметры `page` и `size`, но интерфейс загружает только первые 30 записей и не позволяет запросить следующие |
| Создание нового заказа | ✅ Реализовано | Форма и `POST /api/orders` создают заказ с одной или несколькими позициями и всеми основными параметрами сопровождения |
| Клиент и дополнительные контакты | ✅ Реализовано | В форме доступны необязательный основной клиент и произвольное число дополнительных контактов; исходный и нормализованный телефоны сохраняются отдельно |
| Статусы оплаты заказа | ✅ Реализовано | Пользователь может выбрать `UNPAID`, `PREPAID` или `PAID` при создании и изменить оплату существующего заказа в отдельном редакторе |
| Предоплата и остаток к оплате | ✅ Реализовано | Для частичной оплаты вводится общая внесённая сумма; backend проверяет её границы, а актуальный остаток показывается в строке и полной карточке заказа |
| Статусы исполнения заказа | ✅ Реализовано | Статус можно назначить при создании заказа, увидеть и быстро изменить непосредственно в журнале |
| Способ получения и адрес доставки | ✅ Реализовано | Можно выбрать самовывоз или доставку; для доставки адрес обязателен и отображается в журнале и карточке |
| Комментарий к заказу | ✅ Реализовано | Необязательный комментарий сохраняется вместе с заказом и показывается в раскрытой карточке |
| Просмотр полной карточки заказа | ✅ Реализовано | Карточка содержит позиции, контакты, оплату и остаток, исполнение, способ получения, адрес, комментарий и автора записи |
| Редактирование заказа | 🟡 Частично | Отдельно редактируются статусы исполнения и оплаты; позиции, контакты, получение, адрес и комментарий пока изменить нельзя |
| Быстрая смена статуса | ✅ Реализовано | Статус исполнения изменяется из строки журнала; завершённый или отменённый заказ сразу исчезает из режима «Активные заказы» |
| Поиск старых записей | ❌ Не реализовано | Нет поискового API и интерфейса поиска по телефону, имени, адресу и товару |
| Каталог и автоподстановка товара | ❌ Не реализовано | Позицию можно ввести вручную, но каталога, подсказок, автоматической единицы измерения и рекомендуемой цены нет |

## Технические требования

| Требование | Статус | Что уже работает / чего не хватает |
|---|---|---|
| Архитектура React → Spring Boot → PostgreSQL | ✅ Реализовано | Frontend, backend и база данных работают как единое веб-приложение |
| Модульный монолит backend | ✅ Реализовано | Код разделён как минимум на модули `auth`, `journal` и `common`; отдельные микросервисы не используются |
| React + TypeScript frontend | ✅ Реализовано | Интерфейс создан на React, TypeScript и Vite |
| Java 21 + Spring Boot backend | ✅ Реализовано | REST API, бизнес-логика, валидация и доступ к данным реализованы на Spring Boot |
| PostgreSQL | ✅ Реализовано | Основные данные хранятся в PostgreSQL; база не публикуется наружу в production Compose |
| Миграции Flyway | ✅ Реализовано | Созданы версионированные миграции пользователей, записей журнала, позиций и контактов заказа |
| Модель пользователя | ✅ Реализовано | Хранятся логин, BCrypt-хеш пароля, отображаемое имя, признак активности и дата создания |
| Синхронизация пользователей из конфигурации | ✅ Реализовано | При запуске backend создаёт и обновляет пользователей из `KAMOVED_USERS_N_*`; поддерживаются смена пароля, имени и признака активности без удаления истории |
| Session-based authentication | ✅ Реализовано | Используется серверная HTTP-сессия Spring Security без собственной JWT-инфраструктуры; после входа идентификатор сессии меняется для защиты от фиксации сессии |
| Постоянная сессия не более 7 суток | ✅ Реализовано | Cookie переживает закрытие браузера, имеет `Max-Age=7d`, `HttpOnly`, `SameSite=Lax` и `Secure` в production; сервер дополнительно хранит абсолютный срок от момента входа и не продлевает его активностью пользователя |
| CSRF-защита | ✅ Реализовано | Изменяющие запросы выполняются с CSRF-токеном |
| Модель `JournalEntry` | ✅ Реализовано для текущего MVP | Хранит тип, статусы, суммы, автора, даты, версию, получение, адрес, комментарий, позиции и связанные контакты |
| Модель `JournalEntryItem` | ✅ Реализовано | Хранятся snapshot-название, количество, единица, цена и рассчитанная сумма; ссылка на будущий каталог необязательна |
| Серверный расчёт денег | ✅ Реализовано | Клиент не передаёт итоговые суммы; backend рассчитывает их через `MoneyCalculator` с `RoundingMode.FLOOR` |
| Транзакционное создание продажи | ✅ Реализовано | Запись и все позиции сохраняются в одной транзакции |
| `POST /api/sales` | ✅ Реализовано | Создаёт завершённую и оплаченную продажу текущего пользователя |
| `GET /api/journal` | ✅ Реализовано | Поддерживает режимы `all` и `active`, номер страницы и размер страницы |
| `GET /api/journal/{id}` | ✅ Реализовано | Возвращает позиции и полную карточку продажи или заказа, включая контакты, предоплату, остаток, получение, адрес, комментарий и версию |
| Backend-фильтрация активных заказов | ✅ Реализовано | Активность вычисляется по типу `ORDER` и набору незавершённых статусов; отдельной таблицы активных заказов нет |
| Расчёт дневной выручки | ✅ Реализовано | Агрегация выполняется в БД отдельно от пагинации, по текущему продавцу и границам московского дня |
| `POST /api/orders` | ✅ Реализовано | Транзакционно создаёт заказ текущего пользователя, рассчитывает суммы и сохраняет позиции, контакты и параметры сопровождения |
| `PATCH /api/orders/{id}/execution-status` | ✅ Реализовано | Быстро меняет только статус исполнения и проверяет версию записи, защищая новое состояние от перезаписи устаревшим запросом |
| `PATCH /api/orders/{id}/payment` | ✅ Реализовано | Меняет статус оплаты и общую внесённую сумму, пересчитывает остаток и проверяет версию записи |
| `PATCH /api/orders/{id}` | ❌ Не реализовано | Нет общего редактирования позиций, контактов, получения, адреса и комментария |

## Общая готовность MVP

Из пяти ключевых пользовательских сценариев полностью готовы четыре:

1. Создать продажу из наличия.
2. Создать новый заказ.
3. Посмотреть последние записи журнала.
4. Посмотреть активные заказы.

Для завершения исходного набора ключевых сценариев остаётся поиск старых записей. Быстрая смена статуса уже позволяет сопровождать заказ до завершения или отмены; полное редактирование остальных данных заказа пока отсутствует.

## Продуктовый бэклог

Порядок строк: сначала задачи со статусами `🔵 В работе` и `🟡 Частично`, затем новые и запланированные, в конце — `✅ Завершено`. Внутри группы задачи располагаются по продуктовому приоритету. При смене статуса строка перемещается в соответствующую группу, но не удаляется из таблицы.

| Доработка | Статус | Предлагаемые границы |
|---|---|---|
| Запоминание последнего пользователя на устройстве | Запланировано · высокий приоритет | После первого успешного входа запоминать на этом устройстве только идентификатор последнего пользователя. При следующем входе показывать его имя и сразу запрашивать только пароль, а после внедрения СМС-авторизации — код из СМС. Не сохранять пароль или СМС-код. Добавить заметное действие «Войти другим пользователем»; после его успешного входа запоминать уже его |
| Комментарий к продаже из наличия | Запланировано | Добавить необязательное многострочное поле в форму прямой продажи, сохранять текст в существующем поле `journal_entry.comment` и показывать его при раскрытии записи. Пустой комментарий не хранить и не отображать |
| Фавикон приложения | ✅ Завершено | Добавлены favicon в форматах ICO и PNG для основных размеров; подключение зафиксировано в `frontend/index.html` и вошло в `develop` |
| Приоритетная сортировка бэклога | ✅ Завершено | Закреплено правило «в работе и частично готово → новое и запланированное → завершённое»; завершённые задачи сохраняются в конце таблицы |
| Вход без повторного ввода пароля в течение недели | ✅ Завершено | Вход сохраняется после закрытия браузера не более чем на 7 суток от успешной авторизации; явный выход немедленно инвалидирует серверную сессию и удаляет защищённую cookie. Повышенный риск принят для небольшой семейной системы без критичных и финансовых действий |

## Бэклог обсуждений

Для этой таблицы действует тот же порядок: частично проработанные темы, затем новые, в конце — решённые.

| Тема | Статус | Что нужно решить |
|---|---|---|
| Концепция бренда и маскота | 🟡 Частично | Концепция обсуждена с дизайнером. Следующий шаг — зафиксировать результат обсуждения: образ, характер и роль маскота, базовые цвета и тон бренда, а также определить первые точки применения в продукте |
| Иконки статусов | 🟡 Частично | Механика смены статуса уже выбрана. Теперь нужно определить понятные иконки для состояний и проверить, что они помогают различать этапы, а не перегружают строку журнала |
| Упрощённая авторизация с паролем как резервным способом | Новое обсуждение | Выбрать основной сценарий: вход по номеру телефона с одноразовым кодом из СМС, либо passkey/WebAuthn с отпечатком пальца или биометрией устройства; сравнить простоту для родителей, стоимость СМС и зависимость от конкретного устройства. Определить привязку и подтверждение номера, лимиты и срок жизни СМС-кода, защиту от перебора, восстановление доступа и оставить текущий пароль как резервный способ |
| Механика быстрой смены статуса | ✅ Решено | Выбрано изменение статуса из компактного списка непосредственно в строке журнала; решение реализовано |

## Рекомендуемая последовательность следующих доработок

1. **Запоминание последнего пользователя** — показывать последнего пользователя устройства и запрашивать только пароль, сохраняя возможность войти под другим логином.
2. **Полное редактирование заказа** — позиции, контакты, получение и комментарий с уже подготовленной защитой от одновременного изменения.
3. **Поиск** — по имени, телефону, адресу и товару.
4. **Каталог товаров** — autocomplete, предлагаемая единица измерения и цена с возможностью ручного изменения.
5. **Пользовательская пагинация** — загрузка записей старше первых 30.

Ближайшим вертикальным срезом рекомендуется запоминание последнего пользователя: недельная сессия уже убирает повторный вход после закрытия браузера, а запоминание логина упростит случаи, когда пароль всё же потребуется. После неё — полное редактирование заказа: статусы исполнения и оплаты уже меняются отдельно, но ошибки в позициях, контактах и параметрах получения пока нельзя исправить.
